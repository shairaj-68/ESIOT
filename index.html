1. Introduction

An embedded system is a computer built into a larger product to perform a dedicated function under real-time, memory, power and cost limits. Design decides what the hardware and firmware must do and how the work is split; implementation turns that decision into schematics, PCB, drivers, application code and tests.

Operating principle: sensors convert physical quantities to voltages; the microcontroller (MCU) samples them, runs control logic, and drives actuators or communication links. Events are handled either by polling or by interrupts, and timing is derived from a clock and hardware timers.

Why it matters: most electronic products ship with an MCU. Core companies hire for the ability to move from a requirement to working, debuggable hardware and firmware.

Prerequisites

Digital logic, number systems, basic C, microprocessor basics, ADC/DAC fundamentals.

  • By architecture: 8-bit (AVR, 8051), 16-bit (MSP430), 32-bit (ARM Cortex-M, RISC-V)
  • By software model: bare-metal super-loop, interrupt-driven, RTOS-based, embedded Linux
  • By timing: hard real-time, firm real-time, soft real-time

3. Design and implementation workflow

  1. Requirements: inputs, outputs, accuracy, response time, power budget, cost, environment.
  2. Architecture and HW/SW partitioning: choose the MCU by peripherals, memory, speed and power; decide what is done in hardware (timers, DMA) and what in firmware.
  3. Hardware design: schematic, power tree, decoupling, reset and clock circuits, debug header (SWD/JTAG), PCB layout.
  4. Firmware design: pick the model (super-loop, interrupts, RTOS); define layers: drivers, HAL, middleware, application.
  5. Implementation: cross-compile on a host, flash via debugger, bring up clocks, GPIO, UART first.
  6. Test and debug: unit tests, simulation, logic analyser, oscilloscope, in-circuit debugging, hardware-in-the-loop.
  7. Validation and release: temperature, EMI, power-cycle and long-run tests; bootloader and update plan.

Typical safe ISR pattern

volatile uint8_t data_ready = 0;
volatile uint16_t adc_value;

void ADC_IRQHandler(void){      /* keep short */
    adc_value  = ADC->DR;        /* read clears flag */
    data_ready = 1;
}
int main(void){
    init_clock(); init_gpio(); init_adc();
    for(;;){
        if(data_ready){ data_ready = 0; process(adc_value); }
        enter_sleep();            /* wake on next interrupt */
    }
}

Common misconceptions

  • "Faster clock is always better": it raises power and EMI; choose the lowest adequate clock.
  • "volatile makes shared data atomic": it only stops compiler caching. Multi-byte data may need a critical section.
  • "The simulator proves the hardware works": it does not model supply noise, bounce or timing margins.

Advantages and limits

Low cost, small size, low power and flexible firmware updates; limited by memory, CPU speed, real-time constraints, and debugging difficulty compared with PC software.

4. Timing diagram

Observation: processor runs the main loop until the event, completes the current instruction, saves context, runs the ISR, restores context and resumes. Total CPU busy time per event = latency + ISR execution.

5. Key equations

Timer overflow

ftick = fclk / P    Tovf = 2N / ftick

fclk timer clock (Hz), P prescaler, N counter bits. Derivation: one tick lasts 1/ftick; the counter overflows after 2N ticks. Limit: P = 1 gives the finest resolution but the shortest range.

Fast PWM frequency

fPWM = fclk / (P · 2N)    Duty = OCR / 2N (approx.)

Phase-correct PWM counts up and down, so its frequency is half this value.

UART throughput

Bytes/s = baud / bits per frame    8N1 frame = 1 start + 8 data + 1 stop = 10 bits

ADC resolution

LSB = Vref / 2N    Code = floor(Vin / LSB)    SNRideal = 6.02N + 1.76 dB

Nyquist: fs > 2 fmax. Quantisation error is at most ±½ LSB for an ideal converter.

ISR load and power

Load = (CISR / fCPU) · fint    Iavg = Iact·D + Isleep·(1 − D)    Life = Capacity / Iavg

CISR cycles per ISR including entry and exit, fint interrupt rate, D active duty fraction. Load must stay well below 100%; interrupts must also finish before the next arrives.

6. Solved numerical problems

Problem 1 (Easy): Timer overflow

An 8-bit timer runs from a 16 MHz clock with prescaler 64. Find the overflow period.
ftick = 16 MHz / 64 = 250 kHz, tick = 4 µs. Tovf = 256 × 4 µs = 1.024 ms. Interpretation: a periodic 1 ms system tick needs a reload value, not a free-running overflow.

Problem 2 (Moderate): ADC resolution

A 12-bit ADC with Vref = 3.3 V reads a 10 mV/°C temperature sensor. Find the LSB, the code at 1.65 V and the temperature step per LSB.
LSB = 3.3 / 4096 = 0.806 mV. Code = 1.65 / 3.3 × 4096 = 2048. Step = 0.806 mV / (10 mV/°C) = 0.0806 °C. Real accuracy is worse because of noise, reference error and sensor tolerance.

Problem 3 (Moderate): Battery life

A node draws 10 mA when active for 2% of the time and 5 µA asleep. A battery has 220 mAh. Estimate life.
Iavg = 10 mA × 0.02 + 0.005 mA × 0.98 = 0.2 + 0.0049 = 0.2049 mA. Life = 220 / 0.2049 ≈ 1074 h ≈ 44.7 days. Interpretation: the active duty cycle dominates; halving it matters more than reducing sleep current.

Problem 4 (GATE-style, Difficult): ISR load

A 48 MHz CPU receives interrupts at 10 kHz. Each ISR takes 240 cycles including entry and exit. Find CPU load and the free time per period.
ISR time = 240 / 48 MHz = 5 µs. Period = 100 µs. Load = 5 / 100 = 5%; free time = 95 µs per period. Shortcut: Load = CISR × fint / fCPU = 240 × 10⁴ / 48 × 10⁶ = 0.05.

9. Applications and industry relevance

Automotive
ECUs, BMS, body control; CAN/LIN buses; functional-safety and watchdog design.
Industrial
PLCs, motor drives, sensors on RS-485/Modbus; long life and EMC robustness.
Consumer and wearables
Fitness bands, smart-home nodes; battery life and BLE, OTA updates.
Medical
Infusion pumps, glucose meters; reliability, traceability, safe fail states.
Test and validation
Automated hardware test benches that drive devices over Bluetooth, UART or GPIO and log results.
IoT / smart metering
Low-power sensors, LoRa/NB-IoT links, secure bootloaders.

Design considerations: cost per unit, power budget, EMI, supply-chain availability, certification, and field-update strategy. Common challenges: intermittent bugs from race conditions, brown-outs, clock errors, noisy ADC readings, stack overflow, and hard-to-reproduce timing faults. Roles: embedded firmware engineer, hardware test/validation engineer, board bring-up engineer, FPGA/VLSI verification engineer, IoT engineer.

Polling versus interrupt versus RTOS

Super-loop: simplest. Interrupts: fast reaction, low power. RTOS: many concurrent tasks with deadlines; costs RAM and needs synchronisation.

Quick notes and memory aids

  • Short ISR: set flag, clear source, leave.
  • Shared with ISR: volatile plus atomic access.
  • Open-drain bus: pull-ups required.
  • Bring-up order: power, clock, reset, debug, GPIO, UART, the rest.
  • ADC rule: Nyquist, anti-alias filter, stable reference.
